# 微服务部署与验活 Runbook

本文档对应阶段3 P3/P4 收口，目标不是“看起来像微服务”，而是给出当前仓库真实可执行的本地部署、迁移、启动、验活、故障排查闭环。

## 1. 适用范围

当前仓库已经具备：
- gateway + 15 个 HTTP 服务 + 2 个 worker 的单仓多进程运行形态
- MySQL / Redis / RabbitMQ 本地依赖编排
- 服务级迁移入口
- 健康检查与 readiness 契约
- DB outbox + RabbitMQ / DB fallback 的事件治理基线
- Prometheus + Jaeger + Loki/Promtail/Grafana 本地观测闭环
- 服务级 release 打包、promote、rollback 脚本与 CI 校验 workflow

当前不具备：
- 分库分 schema
- 远端制品仓库 / 审批 / 灰度发布流水线

当前结论：
- 已满足“可独立启动、可分服务迁移、可分服务验活、具备基础治理能力”的运行目标
- 未进入“独立数据库自治、完全独立发布流水线”的终态

约定：

CI 校验：
```text

  - go test ./...
  - go vet ./...
  - shell 语法检查

  - release 打包检查
```

### 5.5 服务级晋级与回滚

晋级指定服务：
```bash
cd /Users/leon/project/game-admin
./scripts/promote-release.sh gateway-service identity-service notification-service
```

回滚指定服务：
```bash
cd /Users/leon/project/game-admin
./scripts/rollback-release.sh gateway-service
```

运行时目录：
```text
deploy/runtime/microservices/
  releases/<service>/<release-id>/
  current/<service> -> ../releases/<service>/<release-id>
  previous/<service> -> ../releases/<service>/<release-id>
```

约定：
- `promote-release.sh` 会先校验 `SHA256SUMS`，再按 `manifest.json` 的 `builtAtUTC + gitCommit` 生成 `release-id`
- 候选制品仍来自 `deploy/releases/microservices/<service>`
- 首次晋级时若 `.env` 不存在，会由 `.env.example` 自动初始化
- `rollback-release.sh` 会把 `current` 切回 `previous`，并自动回填更老一个版本到 `previous`

### 6.3 判定规则

- `/healthz`：只表示进程活着
- `/readyz`：表示依赖可用、可以接流量
- `/metrics`：Prometheus exposition，统一包含 Go runtime、HTTP 请求总数/耗时、ready 状态，以及 worker 轮询/投递/锁获取指标
- worker `/readyz`：会检查 DB / Redis / MQ
- gateway `/readyz`：会逐个主动探测 `servicedef.HTTPList()` 中全部 HTTP 上游的 `/readyz`，并透传 `X-Request-ID` / `X-Trace-ID`
- gateway `/readyz`：任一关键上游返回非 `200`、超时或网络错误时，gateway 会返回 `503`，响应体里保留依赖明细
- worker 失败重试统一采用指数退避：`5s -> 10s -> 20s -> 40s -> 80s(cap)`；超过 `max_attempts` 后进入 `dead_letter`

## 7. 同步调用边界值班说明

- 允许的服务间同步调用只走 `backend/internal/contract/*` 与 `backend/internal/syncclient`
- 当前登记边界：`risk -> report/account/withdrawal`、`withdrawal -> account/risk`、`recalculation -> settlement`
- `backend/internal/architecture/sync_boundary_test.go` 会阻止新增未登记的 `internal/services/*` 直连 import
- `withdrawal-service` 放款成功后若本地事务失败，会调用 `risk-service /internal/contracts/risk/restore-pending-cases` 做最佳努力补偿；这不是 saga 终态，只是当前过渡态止血
- MQ consumer 会先对 `queued` delivery 做原子抢占，避免 RabbitMQ 重复消息并发消费
- 入站支持 `traceparent`；当 `X-Trace-ID` 缺失时，服务会把 W3C trace id 映射到当前 `traceID`
- 已接入官方 OpenTelemetry Go SDK + OTLP HTTP exporter；默认仍保持 `TELEMETRY_ENABLED=false`
- 配置项：`TELEMETRY_ENABLED`、`TELEMETRY_EXPORTER=otlp|none`、`OTEL_EXPORTER_OTLP_ENDPOINT`、`OTEL_EXPORTER_OTLP_INSECURE`、`SERVICE_VERSION`
- 本地 observability profile 提供 `jaeger(:16686)`，默认 OTLP HTTP 地址可指向 `http://jaeger:4318`
- compose 启动时会把 backend/gateway/worker stdout/stderr 追加到 `deploy/observability/logs/<service>.log`

### 6.4 Prometheus 抓取清单

- compose `observability` profile 会启动 `prometheus(:9090)`，配置文件位于 `deploy/observability/prometheus.microservices.yml`
- compose `observability` profile 还会启动 `jaeger(:16686/:4317/:4318)`，用于接收 OTLP traces
- compose `observability` profile 已补 `loki(:3100)`、`promtail`、`grafana(:3000)`，用于结构化日志采集和查询
- `scripts/observability.sh` 提供 `start|stop|status|smoke|logs` 统一入口，避免每次手写 compose 命令
- `gateway` 通过 `gateway:8080/metrics` 抓取
- 全部 HTTP 服务通过各自服务端口的 `/metrics` 抓取
- worker 通过 `notification-service:8095/metrics`、`data-platform-sync-service:8096/metrics` 抓取
- 当前指标标签只保留 `service/component/method/route/status_class/consumer/mode/stage/result`，不把 `requestID/traceID` 作为 label，避免高基数

### 6.5 日志查询口径

- promtail 采集源：`deploy/observability/logs/*.log`
- loki 基础标签：`job=game-admin-services`、`service=<service-name>`
- Grafana 已预置 `Prometheus` 与 `Loki` datasource，无需手工配置
- 推荐 LogQL：
  - `{job="game-admin-services"} | json`
  - `{job="game-admin-services",service="gateway-service"} | json | level="ERROR"`
  - `{job="game-admin-services",service="notification-service"} | json | component="worker"`

## 11. 风险与边界

1. 当前共享 schema
- 这是单仓多服务，不是独立数据库自治

2. 当前无独立发布流水线
- 只能证明“可运行、可迁移、可验活”，还不是“可灰度、可回滚、可独立发版”终态

3. 当前多租户隔离未全量收口
- service / table 级别已覆盖很多，但缓存 key / MQ topic / 外部资源路径还没全量统一

4. 当前规则平台未统一
- commission / activity / risk 仍是分域演进，不是统一规则中台

5. 当前补偿链仍是最佳努力
- `withdrawal-service` 放款成功后若本地事务失败，会调用 `risk-service /internal/contracts/risk/restore-pending-cases` 做补偿恢复
- 当前已验证 `risk.case.released -> risk.case.restored` 本地闭环
- 但这仍不是持久化 saga 编排

6. 当前结构化日志已补基线但日志采集流水线仍欠账
- 运行时与 HTTP 请求日志已结构化
- request/trace header 已做归一化与随机 ID 回填
- 已补 Prometheus `/metrics`
- 已接入可开关的 OTLP tracing exporter
- 但集中日志采集/索引流水线仍未落地

## 12. 故障排查

### 12.1 gateway ready 503
先查上游：
```bash
./scripts/run-microservices.sh ready
```
重点看：
- identity-service
- tenant-service
- game-service
- audit-service

### 12.2 worker ready 503
先查中间件：
```bash
curl http://127.0.0.1:8095/readyz
curl http://127.0.0.1:8096/readyz
```
通常是：
- MySQL 没起来
- Redis 没起来
- RabbitMQ 没起来 / MQ 配置不通

### 12.3 事件堆积
现象：
- 业务写成功，但通知/同步没出结果

排查：
1. 看 worker 日志
2. 看 RabbitMQ queue
3. 查 `domain_event_delivery`
4. 看是否进入 `dead_letter`

### 12.4 单服务起不来
排查顺序：
1. 端口占用
2. `DATABASE_DSN`
3. Redis / MQ 开关与地址
4. 先单独跑对应 migrate-service
