### 1.1 当前架构结论

结论：当前仓库已经从“单 Go 进程承载全部 API”推进到“单仓可运行多服务 + 网关治理 + outbox/MQ 事件治理 + 服务级部署脚本与验活”的过渡态微服务架构。

这意味着：
- 已满足“可独立启动、可分服务迁移、可分服务验活、具备基础治理能力”的当前运行目标
- 仍未满足“独立数据库自治、独立发布流水线终态、统一规则平台终态、数据中台成品化”的终态目标

一句话：不是假微服务壳子了，但也还没到完全自治微服务终局。

- `/healthz`
- `/readyz`
- `/metrics`（Prometheus exposition，统一暴露 runtime / HTTP / worker 指标）
- `/api/enum-dictionaries`

gateway 运行时治理补充：

- `/healthz` 只表示 gateway 进程存活，不参与上游依赖判定
- `/readyz` 会读取 `config.Gateway.TargetFor(...)` 与 `servicedef.HTTPList()`，逐个主动探测各 HTTP 上游的 `/readyz`
- 探测会透传 `X-Request-ID` / `X-Trace-ID`，并把超时、网络错误、非 `200` 状态统一收敛到 `app.DependencyHealth`
- 任一关键上游失败时，gateway `/readyz` 返回 `503`，同时保留依赖明细，便于流量摘除和故障定位

## 3. 基础设施职责

### 3.1 MySQL

- 统一 OLTP 主库
- 承载租户、品牌、代理、用户、角色、订单、账务等事务数据
- 当前服务仍是共享库表，尚未做到物理分库

### 3.2 Redis

- 规则命中缓存
- 权限缓存
- 幂等键
- 分布式锁
- 临时任务状态

当前代码已在启动期探活，业务缓存语义仍需继续下沉到各服务内部。

### 3.3 RabbitMQ

- 充值事件
- 结算事件
- 提现事件
- 风控事件
- 通知事件
- 数仓同步事件

当前代码已落地“DB outbox + MQ transport abstraction”事件总线：

- `domain_event` / `domain_event_delivery` 负责事件落库、消费者投递状态与重试
- `domain_event.payload` 已统一收敛为事件 envelope：`eventType`、`aggregate(type/id)`、`version`、`requestID`、`traceID`、`idempotencyKey`、`occurredAt`、`payload`、`meta`
- `tenant` / `brand` / `platform_config` / `game` / `game_access` / `game_credential` / `rbac_role` / `rbac_user` / `invite_code` / `player_register_with_invite` / `binding` / `agent_invite_application` / `agent_relation` / `recalculation_task` / `recharge` / `settlement` / `withdrawal` / `risk` / `activity` 写路径已发布领域事件
- HTTP 侧 `operation_audit_log` 写入也已同步发出审计领域事件
- MQ 开启时，worker 会先把待投递 delivery 分发到 transport 对应队列，再消费并回写投递状态；当前 RabbitMQ 默认实现通过长连接 AMQP channel 完成这一步
- MQ 关闭时，worker 回退为直接轮询 DB outbox 消费
- 本轮补齐 delivery 治理字段：`max_attempts`、`last_attempted_at`、`last_published_at`、`dead_lettered_at`、`dead_letter_reason`、`dead_letter_payload`、`source_transport`
- worker 在 MQ consume 阶段会先对 `queued -> processing` 做原子抢占，避免重复消息并发消费
- 重试策略已统一为指数退避：`5s -> 10s -> 20s -> 40s -> 80s(cap)`；达到 `max_attempts` 后转为 `dead_letter`

因此当前 RabbitMQ 已不再只是探活占位，而是通过可切换 transport 接入；outbox 仍是系统记录、重试与死信收口基线。

## 4. 当前代码架构的真实边界

### 4.1 已完成的微服务运行时边界

- 各服务已经具备独立 `cmd/*-service` 入口
- 服务模块与路由映射集中在 `internal/servicedef`、`internal/routing`
- 网关转发边界已形成
- worker 与 HTTP 服务职责已拆开
- 迁移入口独立到 `migrate-service`
- 本轮补齐统一治理基线：
  - `/healthz` + `/readyz` 统一契约
  - 健康响应统一包含 `status/service/version/timestamp/requestID/traceID/dependencies`
  - request id / trace id 在 HTTP 中间件统一生成、透传、回写
  - 统一 JSON 输出 helper，错误响应也附带 `requestID/traceID`
  - 审计写路径从 HTTP -> audit service -> `operation_audit_log` 全链路补齐 `traceID`

### 4.2 仍保留的共享边界

当前仍不是完全独立仓库/独立数据库的终局微服务，保留以下共享边界：

- 共享单仓代码库
- 共享 `internal/domain/model`
- 共享一套数据库 schema
- 共享部分 `shared` service / helper
- 跨服务调用多数仍以同仓服务装配为主，尚未全部升级为严格远程调用

因此当前系统更准确地说是“单仓可运行多服务 + 事件总线 + 网关治理”的微服务过渡态。

### 4.3 同步调用边界

当前代码把同步调用边界收敛为三类：

1. `gateway -> HTTP service`
- 允许
- 统一经过 gateway 路由表与 `config.Gateway.TargetFor(...)`
- HTTP 治理入口统一收敛到 `internal/syncclient`
- 必须带 `X-Request-ID` / `X-Trace-ID`
- 必须设置超时
- 非 `2xx` 状态统一包装为状态码错误

2. `service -> service`
- 仅允许发生在明确声明的 contract 层
- 当前已落地：
  - `risk-service -> report-service(team-performance contract)`
  - `risk-service -> account-service(account-ledger contract)`
  - `risk-service -> account-service(risk-accounts/risk-account-snapshot contract)`
  - `risk-service -> withdrawal-service(risk-signals/latest-risk-withdrawal contract)`
  - `recalculation-service -> settlement-service(generate-bill contract)`
  - `withdrawal-service -> account-service(account-ledger contract)`
  - `withdrawal-service -> risk-service(release-pending-cases/restore-pending-cases contract)`
- 代码上不再直接在业务逻辑里 new 目标 service 并跨域调用，而是通过 `internal/contract/*` 注入客户端接口
- `risk-service`、`withdrawal-service`、`recalculation-service` 的默认构造也已改走 contract 本地客户端，不再直接 import 其他 `internal/services/*`
- contract 入口保留 `context.Context`，用于 requestID / traceID 透传与未来远程化切换
- `backend/internal/architecture/sync_boundary_test.go` 会扫描 `internal/services/*` import，阻止新增未登记的跨服务直接耦合

3. `service -> shared DB/schema`
- 当前仍大量存在
- 这是当前过渡态架构的已知边界，不属于允许长期保留的终态同步调用方式
- 文档层明确列为剩余风险，不再把它误判成“已完成微服务自治”

当前审计出的同步耦合清单：

- `gateway-service` 主动探测上游 `/readyz`
- `risk-service` 风险情报聚合依赖 `report-service` 的 `team-performance` contract
- `risk-service` 风控冻结/释放依赖 `account-service` 的 `account-ledger` contract
- `risk-service` 风险账户/提现读模型依赖 `account-service` 与 `withdrawal-service` 的 internal contract 读接口
- `recalculation-service` 生成结算单依赖 `settlement-service` 的 `generate-bill` contract
- `withdrawal-service` 账户冻结/解冻/结算依赖 `account-service` 的 `account-ledger` contract
- `withdrawal-service` 放款成功后的风控释放依赖 `risk-service` 的 `release-pending-cases` contract；若后续事务失败则走 `restore-pending-cases` 补偿，并发布 `risk.case.restored` 事件
- 所有 HTTP 服务 / worker 仍共享同一 MySQL schema 与 `internal/domain/model`

### 4.3 日志与可观测性当前状态

本轮已把最基础的结构化日志补齐到运行时入口：

- `backend/internal/app/logger.go` 提供统一 JSON logger
- HTTP runtime 启动日志已带 `service/address/modules/component`
- gateway runtime 启动/失败日志已结构化
- worker runtime 启动/失败日志已结构化
- HTTP 请求完成日志已统一为 `service/component/requestID/traceID/method/path/status/error/duration_ms`
- gateway proxy 失败路径、worker 投递失败/死信路径已落同一字段规范
- 入站已支持 `traceparent` 解析；当 `X-Trace-ID` 缺失时，会映射 W3C trace id 到当前 `traceID`
- 下游同步调用会继续透传 `X-Request-ID` / `X-Trace-ID`，并在 trace id 为合法 32 位 hex 时补发 `traceparent`
- 已接入官方 OpenTelemetry Go SDK + OTLP HTTP exporter，默认关闭；当前已覆盖 `http.request`、`gateway.proxy`、`gateway.ready_probe`、`worker.publish`、`worker.consume`
- telemetry runtime 已补回归测试，覆盖 disabled、非法 exporter 和 OTLP HTTP flush 到 collector 三条路径
- compose 观测侧已补 `loki + promtail + grafana`，backend/gateway/worker 会把 stdout/stderr 落到 `deploy/observability/logs/<service>.log` 并自动被采集
- `/healthz` `/readyz` 仍保持统一 JSON 契约
- `X-Response-Time-Ms` 继续保留为最轻量延迟观测出口

当前可观测性仍未补齐：
- 更细粒度的业务域指标与告警规则
- 远端集中化日志保留策略与权限隔离

## 7. 推荐改造顺序

### P0 串行优先
1. 全量 tenant / brand 隔离收口
- why: 这是活动、提现、风控、数仓继续演进的共同前置条件

### P1 可并行
2. 统一规则平台抽象
3. service-local repository 与 shared model 继续解耦

### P2 可并行
4. 活动奖励中心闭环增强
5. 提现财务链路增强
6. 智能风控接入

### P3 串行偏后
7. 数据中台成品化（ODS/DWD/DWS/BI）

### P4 最后收口
8. 独立发布流水线
9. 数据自治 / 分库分 schema

## 8. 并行 / 串行关系

必须串行：

- tenant/brand 全链路隔离 -> 数据中台成品化
- tenant/brand 全链路隔离 -> 数据自治
- 统一规则平台 -> 活动/风控高级规则能力
- 事件契约稳定 -> 数仓指标层建设

可以并行：

- 活动奖励中心增强 <-> 提现财务增强
- 活动奖励中心增强 <-> 智能风控接入
- repository 继续下沉 <-> 发布构件完善
- worker/事件契约补强 <-> 报表扩展

不建议并行：

- tenant 隔离未收口时，同时推进数仓成品化 + 服务拆库
- 统一规则平台未定稿时，同时大规模扩活动 DSL + 风控 DSL

## 9. 当前结论

当前系统已经不是“看起来像微服务”，而是已经进入“单仓可运行多服务 + 网关 + outbox + worker + 健康治理基线”的真实过渡态。

但距离完全自治微服务终态，仍有三类核心缺口：

1. 数据与租户边界还不够硬
2. 业务平台化（活动 / 提现 / 智能风控 / 数仓）还未完全闭环
3. 发布治理与数据自治还未完成

因此，当前系统可以判定为：

- 运行时拆分：大体完成
- 治理基线：本轮补齐到可交付状态
- 平台化深水区：仍在进行中
- 终局微服务自治：未完成
